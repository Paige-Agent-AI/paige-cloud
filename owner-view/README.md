# PAIGE Cloud owner deployment view

[ANT-177](https://linear.app/paigeagentai/issue/ANT-177) tracks the private dashboard. The public F2 preview is a separate Coolify app. The dashboard reads its HTTPS `/healthz` and `/release.json` endpoints and the provider's application and deployment history metadata. It does not promote or rebuild releases. The accepted [F2 release evidence](https://linear.app/paigeagentai/issue/ANT-176) supplies the deployment-to-digest mapping. A new or ambiguous deployment, a changed digest, and a conflicting source manifest all leave the release unconfirmed.

The owner overview also checks PAIGE Agent AI's three production domains through public HTTPS GET requests. It reports a shared source commit when all three release manifests agree. Production digest verification remains tied to the release and provider evidence. The Coolify read token stays scoped to the F2 application. See the [SaaS readiness assessment](../docs/11-saas-readiness.md).

## Project access

The owner uses the original key once at `/setup` on the primary hostname. Setup creates an email-and-password account for the existing `cloud-owner` identity and closes the setup route. The Cloud membership database stores that identity's read grant for the `paige` organization's `paige-agent-ai` project. The project's registered environments are `production` and `f2-preview`. Each environment inherits the project's read grant and has its own status reader. Production reads public manifests and health endpoints. The F2 reader alone uses the Coolify token.

The console uses `GET /accounts/{number}/api/organizations/paige/projects/paige-agent-ai/status`. Add `/environments/{environmentId}` before `/status` to read a single environment. The legacy `GET /api/status` checks the same project grant for the signed-in principal. The server checks the session, account number, and grant before it consults the cache or calls a reader. An authenticated request for a different account returns HTTP 404.

**Production release receipts** on Deployments uses reviewed, retained records in `production-receipts.json`. Copy the allowlisted fields from a successful exact-source `paige-production-receipt.json` artifact and include its GitHub artifact ID in a reviewed Cloud source update. Preserve earlier verified rows. The console checks each public domain for health and the live commit on refresh. A commit match compares the public manifests with the receipt; the displayed digest and rollback target come from GitHub's recorded promotion. A new live commit without a stored receipt is labeled accordingly.

**Live GitHub build activity.** Supply `OWNER_VIEW_GITHUB_BUILD_WEBHOOK_SECRET` as a runtime-only lowercase 64-character random hex secret. Configure JSON webhooks on the canonical PAIGE Agent AI repository for push, pull request, and workflow run events, and on the Cloud repository for workflow run events. Point both to `/hooks/github-builds` on the console's HTTPS origin and use the same secret. The console writes bounded build observations to `github-builds.sqlite` on the existing private volume. The signed-in Deployments page receives updates as events arrive and measures elapsed time from the source run timestamps. Main pushes invalidate the cached GitHub reference. Domain readbacks continue while Deployments is visible. Release receipts still require verified provider evidence.

To start isolated preview builds on same-repository PR events, supply `OWNER_VIEW_PREVIEW_DISPATCH_TOKEN` with Actions write access limited to the private Cloud preview repository. Keep the existing read-only preview inventory credential separate. The dispatcher queues each eligible PR head once, checks availability against the latest observed head, and uses the existing GitHub workflow that revalidates the head and builds with inert settings. Its image still goes through the existing preview deployment procedure. Inspect unconfirmed requests in Actions before retrying. Production promotion continues through the approved `main` workflow and its required CI. Check delivery logs and redeliver missed events after outages. Verify the proxy passes the event stream through without buffering.

**Pull request previews** lists open PAIGE Agent AI pull requests and their current head commits. Configure `OWNER_VIEW_PREVIEW_ACTIONS_TOKEN` at runtime with read access to Actions in the private Cloud repository only. This supplies queued, building, failed, and passed statuses. The console shows a preview link after reading back both the current PR head and the matching Cloud builder commit. The existing pilot retains its URL.

For a preview request in Linear, run **Build a PAIGE pull-request preview** with the PR number and full head SHA. Download that successful run's `paige-pr-preview.json`, then use the existing Cloud operator credential with `node scripts/deploy-pr-preview.mjs <receipt>`. The command checks the current PR head again and uses its stable HTTPS address on the separate preview destination. Start with eligible requests in the existing release order. The build workflow does not deploy automatically.

Project readers are bound in source. Memberships use the exact principal, organization and project tuple in a private SQLite file. The server rechecks the grant before responding, including after an in-flight read. The console clears displayed data when its next status request returns a project denial.

After owner setup, approved evaluators can create an account at `/signup`. The operator-only command `node accounts.mjs invite <email>` still creates a 48-hour account invitation without a project grant. Deliver these codes privately. Treat the accounts database as credential material. Only salted password hashes are stored.

## Domains, activity, and media

Domains displays the latest HTTPS probe and reported frontend commit for each PAIGE production host. Activity links recorded releases and preview build events to their account-scoped deployment detail URLs. A preview detail URL is bound to its PR head and becomes unavailable if that head leaves the current preview inventory. Evidence links open the recorded GitHub run or release receipt.

For private broadcasts, configure `OWNER_VIEW_STREAM_ACCOUNT_ID`, `OWNER_VIEW_STREAM_TOKEN` (Cloudflare Stream access including token signing), and `OWNER_VIEW_STREAM_PLAYBACK_HOST` (the exact `customer-….cloudflarestream.com` hostname) as console runtime settings. The feature uses the existing project and membership database. Rollback images leave its additive stream records intact.

Create a fresh live input in the connected Cloudflare account with automatic recording and signed playback enabled. Register its input ID and an event title in the project’s Media page. Copy the Member watch link from that page and broadcast through OBS using credentials from Cloudflare. The same watch link serves the live video and its replay. It resolves to each signed-in project member’s account route. PAIGE Cloud never reads ingest keys into the browser. Playback tokens expire at the end of the current console session. Use a new input for each event.

The self-hosted MediaMTX pilot is available under **PAIGE Agent AI → Media** when the console is configured with `OWNER_VIEW_MEDIA_PILOT_ORIGIN` and `OWNER_VIEW_MEDIA_PILOT_KEY`. Deploy `media-pilot/` as a separate Coolify image application with `/recordings` mounted as a Docker volume. Give it the same random 64-character hex runtime key as `PAIGE_MEDIA_ORIGIN_KEY`. Map only container port 8080 through the HTTPS proxy, cap CPU and memory, and leave auto-deploy off. Container health is `/healthz`. The publisher, HLS server, replay exporter, and MediaMTX API listen on loopback.

The owner can start one 75-second synthetic broadcast. The signed-in watch page switches to the recorded replay after the broadcast. Existing project membership governs access to the watch page and individual media requests. The private MP4 and one-time start marker persist with the volume. The pilot has no external ingest or reset control.

## Projects and members

For a new customer, open **Projects → Invite a customer**, enter their email and first project name, and send the prepared email draft. The customer signs up with the email and the single-use, 48-hour invitation code. Signup creates their account, account number, organization, first project, and project grant in one transaction. When they sign in, they land on their new project. The owner can reissue or cancel a pending invitation in Projects. Use the project's **Members** page to invite a teammate to an existing project. When both invitation types are pending for a new email, use the customer invitation for signup and accept the teammate invitation after signing in.

Open **Projects** to create a project, edit its display name, or archive and restore it. Organization and project IDs remain stable. PAIGE Agent AI has a fixed display name and stays connected to its reviewed deployment readers. New projects are private records until connected to their own deployment source.

Each sign-in receives a stable, randomly assigned 12-digit account number from the private account database. The account prefix `/accounts/{number}` is followed by `/overview`, `/deployments`, `/projects`, `/projects/{organizationId}/{projectId}`, the owner-only `/projects/{organizationId}/{projectId}/members`, or `/join`. Short page links redirect to the signed-in account. Each user still needs a project grant to open that project, even if someone shares a link. Account numbers are identifiers only. Include the existing accounts database in backup and restore to preserve its number mappings.

In a project, the Cloud owner can prepare an invitation for one email. **Open email draft** opens the selected mail app with the address, setup instructions, and a 48-hour code. The owner sends the draft. An invited evaluator creates an account if needed, signs in, and enters the same code under **Accept an invitation**. Acceptance grants access to that one project. Pending invitations can be cancelled. Revocation takes effect on the member's next project request and cancels any pending invitation to the same member for that project.

The console extends the existing membership file on startup in a SQLite transaction. Existing grants are preserved. Archived projects retain their IDs and grants for restoration, while active member access and pending invitations are closed. Keep both database files on the **same** private local volume in rollback-journal mode.

For recovery, keep the console offline while reconciling membership changes and archived projects since the snapshot. Use a trusted SQLite client on the membership database to invalidate restored invitations with `DELETE FROM project_invitations` and, when the table exists, `DELETE FROM customer_invitations`. Reissue the current invitations after verification. The post-enrollment PR #7 image can read the original grants on the same file and only serves the canonical deployment reader. Invalidate outstanding invitations before resuming catalogue operation after any rollback that used older membership tools.

### Membership storage and administration

- Mount a private local volume on the owner console, for example at `/var/lib/paige-cloud`. Use a local filesystem that supports SQLite locking and hard links. Give the container's `node` user read and write access to the private directory and both databases. Set `OWNER_VIEW_MEMBERSHIP_DB` to the absolute file path under the mount, for example `/var/lib/paige-cloud/memberships.sqlite`. Verify actual mount and write access before deploying the catalog.
- Run `node memberships.mjs init` once for an empty installation to seed the schema and first owner grant. A repeated init checks the existing database and preserves revocations. Console startup requires the existing file and schema, then creates the additive catalog tables without reissuing grants.
- Run `node memberships.mjs grant cloud-owner paige paige-agent-ai` or `node memberships.mjs revoke cloud-owner paige paige-agent-ai` on the same mounted file. These are idempotent local operator commands. After changing a grant, verify the signed-in project status route. Supported project readers and the owner identity still come from the application.
- Before starting the updated image, run `node accounts.mjs init` using its `node` user and the same private mounted directory. It initializes `accounts.sqlite` alongside the membership file. Start the console only after both files are present. Keep a private SQLite-consistent backup of both files, including an accounts backup after owner setup. For recovery, stop only the Cloud owner app and restore the paired files from a known-good backup taken after setup. A lost password requires separate operator-assisted recovery. Keep the account records intact during recovery.
- Use a SQLite-aware backup or stop the writer and console for a consistent offline copy. Reconcile revocations before restarting against a restored copy. Keep the console offline if rolling back to an older image with a hardcoded grant. A database-aware rollback image must support the stored schema and enforce current grants.

## Publish and host

The application detail view records a **desired** provider binding only. With `OWNER_VIEW_BINDING_TARGETS` unset, no targets are selectable. If separately authorized for the environment, supply a restricted server-only JSON array with exactly `organizationId`, `projectId`, `environmentId`, `applicationId`, `id` (displayable alias), `provider` (`coolify`), `resourceId` (opaque provider resource ID), and integer `version` per entry. Do not commit operational values. No URLs or credentials are accepted. Configuration is loaded on process startup: restart with the approved configuration to apply changes. Startup reconciliation durably invalidates bindings whose approvals were removed or changed, even if the old configuration is later restored. Only an explicit owner rebind clears invalidation. Binding writes require the current Cloud owner project grant and revision; granted members can read binding state. This feature does not call a provider, observe health, or authorize deployment.

The separate workload observation on that page is off unless **both** `OWNER_VIEW_WORKLOAD_READ_TOKEN` and `OWNER_VIEW_WORKLOAD_READ_FINGERPRINT` are configured. Use an approved read-only credential restricted to the one intended Coolify resource, not the existing preview reader credential or a deploy token. The fingerprint selects the exact approved binding identity/version; mismatches do not read the provider. A successful observation shows the provider-reported state and read time, not image, rollout, or recovery verification. It does not enable deploy or rollback.
