# Customer Zero account service

The account package uses Cognito for password authentication, email verification, recovery, and token revocation. Its SQL store binds verified issuer and subject to a stable account number. It creates the initial organization and membership together. The runtime database login can call scoped functions without access to the underlying tables. Existing console and application deployments use their current stores.

`artifacts.yaml` supplies a private versioned artifact bucket and the generated secret shared by CloudFront and the account function. `accounts.yaml` declares an isolated Cognito pool, an Aurora PostgreSQL writer, and the account API. Evaluator routes default to disabled. `site-edge.yaml` restricts the evaluator site to one operator-supplied IPv4 address and disables IPv6 at the distribution. The account behavior forwards the session cookie and request origin without caching. The site hostname from the edge stack becomes the exact allowed origin for browser writes. The account function requires the edge's secret before accepting any route, including GET requests.

Package `handler.mjs`, `runtime.mjs`, `workload-observation.mjs`, `mission-control.html`, the dependency manifests and production dependencies. For inspection-enabled releases, include the generated `canonical-spine` directory described below. Keep the operator-only `bootstrap.mjs`, tests and PostgreSQL migrations out of the Lambda artifact. The Mission Control entry validates the Cognito session and account before serving the private workspace shell. Use the existing registry and workload inspection interfaces for infrastructure access.

Create the artifact stack, then the accounts stack with a temporary HTTPS origin and routes disabled. Create the site stack using the resulting API hostname and upload the approved `site/` assets without publishing the bucket. Bootstrap the database twice. Update the accounts stack with the distribution hostname and enable evaluator routes after confirming the exact candidate. Never use the legacy distribution, domain, or production API for this procedure.

The operator migration uses a separate database administrator credential. After the database writer is ready, run `node owner-view/aws-accounts/bootstrap.mjs` with the cluster ARN, administrator secret ARN and provisioned runtime secret ARN in the operator's environment. It checks the migration checksum and verifies the application login with the runtime secret. Do the same readback after a restore. ## Private registry contract

Migration `002-registry.sql` is additive. The operator bootstrap applies it through the existing migration lock and checksum ledger after validating `001`. Run bootstrap twice to verify replay. Older Lambda versions can continue to serve account flows with the additive tables present. Roll back the application artifact to its earlier immutable version if needed. Keep the registry data for forward recovery.

Use an existing verified evaluator session through the private origin. Writes require that origin and JSON. The server derives the actor from the session, then PostgreSQL checks current membership and project grants. Service credentials and public enrollment require separate qualification.

| Method and path | Scope, request and result |
| --- | --- |
| `GET /api/cloud/v1/organizations/{organization}/projects` | An active organization member reads only their explicitly granted projects. Returns IDs, names and project roles. A new organization can return an empty list. |
| `POST /api/cloud/v1/organizations/{organization}/projects` | An organization owner submits `id` and `name`. Creates one project and its creator’s project-owner grant together. Same request returns the existing record. |
| `GET /api/cloud/v1/organizations/{organization}/projects/{project}/applications` | An active project grantee reads the scoped application and environment registrations. |
| `POST /api/cloud/v1/organizations/{organization}/projects/{project}/applications` | A project owner submits `id`, `name`, `kind` (`application` or `service`), `environment` and optional `sourceRepository` (`owner/repository`). Reuse the same application identity and metadata to attach another environment. Returns the application and its environment IDs. |

IDs accept 1–48 lowercase ASCII letters, digits or hyphens, starting with an alphanumeric character. Names accept 1–120 characters. Registry limits are 50 projects per organization, with 100 applications and 50 environments per project. Success is HTTP 200. Bad fields return 400, a missing session returns 401, denied browser origin returns 403, an inaccessible target returns 404, and conflicting metadata or capacity returns 409. Responses are not cached.

Repository coordinates are desired source metadata. Registration does not fetch source, deploy anything, allocate compute, or read provider credentials. Resolve actual source and publish immutable artifacts as separate, independently authorized steps. The operator workbook should consume this contract after the authenticated navigation is approved.

## Independent workload delivery and inspection

Read the registered organization, project, application and environment through the existing registry. Build with `python3 infra/aws/customer-zero/workload/build.py <reviewed-head> <staging-directory>`. CI records both ZIP digests from that exact source. Compare every byte digest before placing either archive in versioned storage. The A and B release manifests distinguish two immutable builds from the same reviewed source. Pin the uploaded object version and base64 ZIP checksum in `workload.yaml`.

Create the small synthetic backend record as a private, versioned object under `workloads/{organization}/{project}/{application}/{environment}/config.json`. The execution role reads that one object version. The caller cannot choose the backend object, version or organization. CloudFormation changes the `live` alias through an independently reviewed change set. Capture the function version before deployment. When rolling back, set `RollbackVersion` to that recorded number and read the exact version and digest back after invocation. Runtime and recovery use AWS artifacts and keep working when GitHub is unavailable.

Apply `workload-stack-policy.json` immediately after creating the stack and read it back before any update. The stack policy denies changes to the execution role, which binds the backend bucket, scope and object version for the lifetime of this workload. A published function version retains its role ARN while IAM policy can change independently, so all workload updates use CloudFormation with that stack policy in force. Qualify a new backend binding separately with its own compatibility and recovery plan. Both stored object versions must be non-null and the code object checksum must match the reviewed build.

The IAM-only `paige.cloud.workload.inspect.v1` operation takes a single `operation` key. A trusted caller invokes the `live` alias scoped to the registered workload. Each observation returns the operation schema, organization/project/application/environment, embedded commit and release variant, UTC observation time, and state. `healthy` requires a successful matching read from the pinned backend version. Any unavailable or mismatched object yields `unavailable`; malformed operations yield `unsupported_operation`. Use the Lambda execution version and code digest as separate provider evidence. The pilot uses Node.js 24 and the managed AWS SDK for its single S3 read. Record the runtime release with deployment evidence.

For authorized PAIGE consumption, Trust supplies the actor and allowed workload scope, Spine describes this versioned read operation, and the caller selects only the alias resolved from the scoped workload binding. This interface offers no credential retrieval or mutate operation. Future writes require existing Trust approval and Work, Harness and Orchestration execution. Use verified observations as inputs to Rail and Intelligence and consume approved inference through Model Fabric. This runtime does not activate any of those consumers.

### Private Mission Control inspection

`POST /api/cloud/v1/organizations/{organization}/projects/{project}/applications/{application}/environments/{environment}/inspection` issues one on-demand inspection from the existing same-origin account session. A workspace URL selects a resource; Cognito and the current SQL project grant establish authority. The Cloud adapter passes those facts to the original Spine `decideGovernedExecution` function with a read capability. The runtime derives the invoke arguments and target from its own binding. No browser-supplied provider identifiers, credentials, modes or operating commands are accepted.

Run `package-spine.mjs <verified-source-directory> <account-package-directory>` with the two exact source files from the pinned PAIGE Agent AI revision declared in that script. The packaging step checks both SHA-256 values and strips TypeScript to produce the original decision function and risk registry in the account archive. Preserve the generated `source.json` in the package. GitHub remains a build source; the running package and rollback artifacts are AWS-resident. Hosted Cloud tests exercise the adapter with deterministic fixtures. The release receipt must separately cover the packaged canonical decision function.

The account stack defaults to inspection disabled. Enable only in the private evaluator with the reviewed organization/project/application/environment and the existing workload's exact `live` alias. Apply migration `003` through the existing bootstrap twice and verify the restricted runtime login. The SQL reservation rechecks active membership, project grant and the registered target and atomically allows one attempt per 30 seconds and up to 24 attempts per organization per UTC day. Every admitted attempt consumes capacity, including failures and ambiguous timeouts. The Lambda client makes a single attempt and stops waiting after 4.5 seconds. The workload's own eight-second deadline still bounds an invocation already accepted by AWS.

An observation reports the reviewed scope, runtime-reported source commit, provider-executed immutable version, observation time, and a SHA-256 of the original returned evidence. Provider failure or invalid, stale and mismatched evidence yields 503. An explicitly observed backend failure returns `unavailable`. The protected Projects UI requests the observation manually. Registration, unavailability, and healthy runtime evidence retain distinct states. Failed observations do not trigger automatic mutation, inference or retry.

### Private incident and recovery drill

Build the private drill artifact with `build.py <reviewed-head> <staging-directory> --private-drill`. The default build contains only normal releases. Publish the drill only to the existing isolated development workload after recording its current healthy version, exact code digest and immutable source. The drill requests a different version of the same private object with the existing scoped role. It makes one actual S3 request. The pinned object, data version, role, permissions, and customer services remain in place. AWS 403 is mapped to a bounded incident reason; the provider response and object identity stay private.

Configure `InspectionRecoveryPoint` only from an independently verified healthy version and commit for that binding. A fresh observation of an explicit denial can propose restoring that version. The proposal identifies the affected scope, serving version, destination and evidence digest. It requires effective change-set review and a check that the serving version still matches the plan. The console has no mutation permission and cannot redeem an approval. Execute through the existing operator release path. Independently invoke the restored alias and verify exact version, code checksum, scope and healthy backend state. Retain the original release and restore a normal staged package as the change-set default before reuse. Exit the drill on the original healthy alias. Never retry a rollout with an ambiguous outcome before reading AWS.

File source, approval, execution, AWS readback, attempts and cost in ANT-176. For deterministic evaluation, run `grade-recovery.mjs <verified-PAIGE-trajectory-registry.ts> <operator-readback-receipt.json>` offline. It uses the digest-pinned original PAIGE Intelligence verdict function to grade diagnosis, scoped planning, authorized execution and independent recovery against provider and change-set receipts. It creates no separate evaluator registry or execution history. Filing in Intelligence, durable Work and automated approval redemption remain separate qualification.
