## Authenticated experience challenge

**Mission Control should open on what needs attention across the chosen organization, with Projects as the path to scoped work.** The approved website organizes discovery into five product areas. Copying those categories into five empty console tabs would hide the tasks an operator can actually do. Use organization → project → application → environment → resource or release as the durable scope. Task navigation can then follow the selected scope. Put verified operations and account settings at their points of use.

## Delivery order for the next consumer

The second-workload qualification uses the private account registry and versioned S3 backend. The inspection contract reports application health from an actual scoped backend read, with the immutable release and observation time. Map it into the existing Trust and Spine read path before exposing authorized observations in Mission Control. Work, Harness and Orchestration remain responsible for any future authorized mutation. Rail, Intelligence and Model Fabric retain their original evidence, evaluation and inference roles. [Workload and cost qualification](https://linear.app/paigeagentai/issue/ANT-176#comment-545cd468-1d32-4d92-8ec2-031211cee11a) · [Workload inspection contract](../infra/aws/customer-zero/README.md#independent-workload-delivery-and-inspection)

1. Register a stable second application in a scoped project, with its environment and source coordinate. Prove identical-request replay and foreign-write denial.
2. Qualify source resolution and an immutable build receipt. Bind the reviewed artifact to the registered application and environment. Use a deterministic manual deploy as the initial supported path, with separate health and serving-source checks and an exact recovery target.
3. Exercise the same backend resource contracts for both consumers through scoped provisioning and restore. Add object access, APIs, functions, events and queues as each consumer can prove an independent use case. Verify cost attribution and cleanup.
4. Surface working operations and attention states inside the approved Mission Control direction. A registry record, desired binding, and provider observation should always remain distinguishable.
5. Connect eligible operations to original systems. Trust and Spine bind intent and capability to actor, scope, approvals and expiry. Vault resolves scoped references. Work, Harness and Orchestration handle durable execution, Action Bus coordinates events, and Rail records declaration, effects and independent readback. Model Fabric applies existing routing, Knowledge/Memory/Skills/MCP supply authorized context, and Intelligence/Evals evaluate verified outcomes. A deterministic operator path and independent recovery stay available.

## Historical F2 preview architecture

The private Cloud repository identifies the public frontend by full commit SHA. GitHub Actions builds and tests a static nginx image from locked dependencies and digest-pinned bases, then publishes the candidate to the private GHCR package. The job records both Git revisions and the image manifest digest.

An authorized operator promotes the digest to the dedicated Docker Image app in the existing Coolify Cloud project. Coolify manages the existing Traefik TLS proxy and the application on the Hostinger KVM 2. It pulls each release by digest. The public browser connects to the HTTPS preview, and Traefik routes to nginx on port 8080.

The governed preview serves no backend or auth endpoints. The build configuration substitutes a reserved invalid backend and the runtime limits browser connections to the preview origin. See [preview security](03-security-design.md) and the [release and rollback runbook](05-rollback-runbook.md).

The legacy Dockerfile previews stay on their recorded URLs. The F2 app uses its own stable origin for the entire deployment and rollback sequence.
